# Mailbox backup metadata repair

This narrowly scoped, root-only utility addresses only `deploy-20261105T221639Z.dump` (0 bytes) and `deploy-20261105T134106Z.dump` (7,489,697 bytes) in `/var/backups/growth`. It does not inspect dump contents or touch any other dump. `--check` is read-only. `--repair` records original metadata in a root-controlled journal, moves the zero-byte artifact into a root-only quarantine, and tightens the remaining backup's permissions without changing its bytes or name. The backup directory is expected to be owned by `growth:growth` with mode 0700.

The journal records the original paths, inode/device identity, size and old mode. A recovery operator may move the quarantined zero-byte file back only if the original path remains absent and the quarantine object's recorded identity matches. The nonempty file remains in place; restore its recorded old mode only under a separately approved maintenance action and only after confirming why the repair is being undone. Do not automatically restore mode 0664 after a failed mailbox deployment: unsafe-permission restoration requires separate founder consent. Preserve the journal and quarantine as the undo record.

The fixed root-controlled directory is `/var/lib/growth-mailbox-backup-repair` (root:root 0700).
Its `journal.json` records device, inode, size, owner, group, link count, modification time and original mode for both fixed filenames before either backup is changed. Paths used for operations are derived from fixed constants, not values loaded from the journal. The empty artifact moves to that directory under its original basename using Linux `renameat2(RENAME_NOREPLACE)`; the operation requires one filesystem and cannot overwrite an existing destination. Neither dump's contents are read or copied. Original inode identity is retained.

`python3 scripts/repair-mailbox-backup-metadata.py --check` is read-only, including when the state directory does not exist. `--repair` is the separately approved mutation. Both require root. There is no environment variable, CLI path override or general backup-repair mode. An existing unsafe audit directory, audit file or lock is refused rather than repaired. Repeat and interrupted runs derive progress from the original durable audit and exact current identities; conflicting paths, metadata or completed-state drift stop execution. A successful receipt reports `state=complete`; a later read-only check must agree.

After repair, independently measure the eligible timestamped cohort: neither of these files may remain an unsafe eligible dump, the nonempty artifact must still have its recorded size/inode at its original path with mode0600, and the empty artifact must still exist in root-controlled quarantine with mode0600. Preserve all unrelated dumps and the existing retention/storage checks. The failed empty artifact is not represented as a valid backup.

Tests exercise real POSIX modes, no-follow opens, hard links, no-replace rename, flock and interruption recovery in an isolated temporary filesystem. The test harness substitutes only the account identity and trusted-root anchor; it is not proof of the production account/ancestor metadata. The Windows Vitest wrapper skips that POSIX-only harness explicitly; its independent Linux results are reported separately. No production mutation is a test.

Run only after the exact script has passed independent review and founder approval, following the live-change gate. This document is not authorization to execute it against a live host. Existing storage-guard behavior is unchanged.
